**Arquitetura do Sistema**

- **Visão geral:** Aplicação Node.js/Express monolítica multi-tenant com módulos Python opcionais (Crawl4AI/Playwright). Ponto de entrada e orquestrador: server.js.
- **Tenancy:** isolamento por API key (validação em requests, arquivos data por tenant).
- **Persistência:** PostgreSQL (quando `DATABASE_URL`/`USE_POSTGRES`), fallback SQLite/JSON em data (README.md).
- **Canais:** widget web (widget.js), link curto (`/l/:shortCode`), WhatsApp (whatsapp-channel.js / webhooks).
- **IA & Extração:** extração (Cheerio/Puppeteer/Crawl4AI) → `pageData` → Decision layers → LLMs (Groq → OpenRouter → OpenAI).
- **Orquestração de decisão:** Decision Core / Orchestrator / CTA Engine / V17–V19 layers controlam comportamento final.
- **Observabilidade / Segurança:** logs estruturados, rate-limits, feature flags centrais e WAF/validações.

**Principais módulos**

- **Núcleo / rotas:** server.js (bootstrap, middlewares, endpoints críticos).
- **Banco / persistência:** database.js (migrations, helpers), data storage.
- **Feature flags:** feature-flags.js (≈49 flags + gates por ENV).
- **Widget:** widget.js (init, capture, checkout detection, calendar).
- **Extração:** `extractPageData` / enhanced-content-extractor.js / crawl4ai_bridge.js.
- **IA/Orquestração:** v17-orchestrator.js, v18-extraction-guard.js, v19-deterministic-engine.js, v14-context-layer.js.
- **Decision & CTA:** decision-engine.js, cta-engine.js, decision-core.js.
- **Leads / Scheduler:** lead-capture.js, lead-capture-score.js, scheduling-manager.js.
- **WhatsApp:** whatsapp-channel.js, whatsapp-integration.js.
- **Short URLs / Checkout:** short-url-generator.js, link-resolver.js.
- **Integrations / infra:** Redis (sessions/cache), Crawl4AI/Puppeteer, providers LLM (keys via ENV).

**Fluxo completo do chat (canal-agnóstico, passo a passo)**

- Entrada: usuário via widget / link curto / webhook WhatsApp.
- Resolve tenant/lead/conversationId → carrega `pageData` (widget may send `checkoutLink`).
- Pipeline inicial: Scheduler-priority (detecta agendamento) — se disparar, retorna calendarHash e finaliza.
- Montagem de contexto: histórico, `pageData`, feature flags, leadId, journeyStage.
- Decision layers: feature-flag-driven orchestration (V17/V19/Decision Core/V12 state prompts) decidem intent/stage/CTA.
- Prompt → chamada LLM (Groq → OpenRouter → OpenAI) com timeouts/circuit-breaker/cache.
- Sanitização/guards (URL guard, checkout authority), injeção de CTA/calendário.
- Persistência: salva conversa, lead, eventos, analytics, appointments.
- Adaptação por canal: widget rende DOM/CTAs, WhatsApp converte para texto/links, link curto redireciona/renderiza.
- Resposta ao usuário e registro de métricas/logs.

**Pipeline das inteligências (resumo das camadas)**

- **V18 — Extraction Guard:** valida confiança da extração (ok/partial/failed) e controla fallback de links.
- **V17 — Unified Brain (opcional):** orquestrador que monta estratégia, prompt e pode bypassar camadas legadas.
- **V19 — Deterministic Decision Engine:** autoridade determinística (modo `shadow|true|false`) para decisão comercial.
- **V14 / V12 / V11:** camadas de contexto, state prompts e RAG/extração avançada (deep context, multipage).
- **Decision Core / CTA Engine:** transforma intent + pageData + history em CTA/ações.
- **LLM Providers cascade + cache:** Groq preferencial → OpenRouter → OpenAI, com LLM cache (`FEATURE_CACHE_V2`) e circuit-breakers.
- **Auto-learning / Observer:** coleta dados para otimização (`FEATURE_AUTO_LEARNING`), logs estruturados e auditoria.

**Feature flags encontradas (principais e impacto)**

- Críticas/alto impacto:
  - `FEATURE_V17_BRAIN` — ativa cérebro unificado (alto risco).
  - `FEATURE_DETERMINISTIC_V19` — torna V19 autoridade final.
  - `FEATURE_CHECKOUT_AUTHORITY` / `FEATURE_V12_FORCE_CHECKOUT` — força injeção de checkout.
  - `FEATURE_AUTO_CHECKOUT_DETECTION` / `FEATURE_SMART_CHECKOUT_SELECTOR` — detecção/seleção de checkout do widget.
  - `WA_USE_FULL_PIPELINE` — controla se WhatsApp usa pipeline completo.
  - `USE_POSTGRES` / `REDIS_URL` gates infra críticas.
- Operacionais/importantes:

- Observação: o inventário central está em feature-flags.js (≈49 flags) — toggles podem mudar comportamento sem deploy.

**Riscos de regressão encontrados (prioritizados)**

- Alterar **server.js**: quebra global de rotas, bootstrap, ordem do pipeline (SCHED-PRIORITY).
- Mudar **schema/DB** (database.js) ou toggling `USE_POSTGRES`: perda/corrompimento de dados tenant.
- Modificar **feature flags críticas** (V17/V19/checkout authority): alterações comportamentais amplas e silenciosas.
- Alterar **widget** (widget.js): mismatch frontend/backend (ex.: front permite nome apenas; backend exige email) → falhas de captura.
- Quebrar **extractPageData / V18**: perda de contexto e checkout detection → impacto em CTA/conversão.
- Remover/alterar marcador `[CALENDAR_WIDGET]` ou algoritmo de `calendarHash` (scheduling-manager): agendamentos quebrados.
- WhatsApp: mudanças em whatsapp-channel.js ou mapping de instância/número podem interromper toda entrega do canal.
- `/api/capture-lead`: validações divergentes (front vs back) podem causar perda de leads ou inconsistência.
- Short-URL / link-resolver / checkout collision: quebra de tracking e conversões.
- In-memory caches (lead-score, rate limit) reiniciam em escala → perda de estado crítico.

**Dependências entre módulos (mapa essencial)**

- **Widget → Server:** widget chama `/api/process-chat-inteligente`, `/api/capture-lead`, `/api/public/availability/:hash` (dependência direta).
- **Extractors → Decision / LLM:** `extractPageData` alimenta `pageData` usado por V18/V17/V19 e prompt LLM.
- **Feature Flags → Todos:** feature-flags.js influencia orquestração, extração, CTA, scheduler e canais.
- **Decision Core / CTA → Persistence:** decisões influenciam gravação de leads/appointments/analytics (dependência em database.js).
- **Scheduler ↔ Lead Capture:** booking exige lead (frontend blocking) e backend scheduling-manager gera/resolves `calendarHash`.
- **WhatsApp → short_urls / extractors:** WA busca `short_urls` e `checkout_links` para contexto; depende de `server-utils.extractPageData`.
- **LLM providers → config/env:** Groq/OpenRouter/OpenAI dependem de chaves ENV; circuit-breakers e cache dependem de feature flags.
- **Analytics / Observer → Auto-learning:** logs estruturados alimentam otimização; mudança em logging flags pode bloquear learning pipeline.
- **Backup systems → leads storage:** DOCUMENTACAO_BACKUP_LEADS.md e rotas admin dependem de formato persistido (JSON vs Postgres).

Observações finais (recomendações rápidas)
- Todo ajuste em flags críticas ou nos arquivos listados como “críticos” (ex.: server.js, database.js, widget.js, feature-flags.js, scheduling-manager.js) exige checklist de regressão (chat, widget, WhatsApp, checkout, scheduler, lead capture).

# Architecture Authority Contracts

Este documento define os contratos de autoridade arquitetural do Link Mágico. Ele deve ser usado como referência oficial para decisões futuras de arquitetura e implementação.

## Contrato 001
Somente `lib/v17-orchestrator.js` pode criar ou alterar a intenção principal (`Intent`) quando `FEATURE_V17_BRAIN` estiver ativo.

## Contrato 002
Somente `lib/v19-deterministic-engine.js` pode criar, remover ou alterar o estado final de CTA e checkout quando `FEATURE_DETERMINISTIC_V19=true`.

## Contrato 003
Somente a camada de Checkout Authority (resolver/links do pipeline central: `lib/v17-link-resolver.js`, `lib/link-resolver.js`, `lib/safe-checkout-resolver.js`) pode definir o checkout final exposto ao cliente.

## Contrato 004
Somente `lib/v17-link-resolver.js` e seus componentes associados do pipeline central podem resolver URLs finais de compra e fallback de WhatsApp para o fluxo de conversão.

## Contrato 005

- **Tenancy:** isolamento por API key (validação em requests, arquivos data por tenant).
